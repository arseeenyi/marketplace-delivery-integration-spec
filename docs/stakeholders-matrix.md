## 2. Карта влияния и интереса (Power/Interest Grid)

### Квадранты и стратегия работы

| Квадрант | Кто попал | Стратегия | Конкретные действия |
|----------|-----------|-----------|---------------------|
| **🔴 Key Players**<br>(Высокое влияние + Высокий интерес) | CPO, CTO | **Управлять вплотную** | Еженедельные встречи 1-на-1, согласование каждого ключевого решения, ранний показ прототипов |
| **🟡 Keep Satisfied**<br>(Высокое влияние + Низкий интерес) | — | **Удовлетворять** | В нашем проекте таких нет. Если бы был, например, гендиректор — информировать о статусе раз в месяц без погружения в детали |
| **🟢 Keep Informed**<br>(Низкое влияние + Высокий интерес) | Руководитель логистики, Главный бухгалтер | **Информировать** | Регулярные демо, приглашение на UAT, согласование форматов данных. Их мнение важно для приёмки, но они не блокируют бюджет |
| **⚪ Monitor**<br>(Низкое влияние + Низкий интерес) | Техлид FastDelivery, DBA, Покупатели | **Мониторить** | Держать в курсе по необходимости. DBA — согласовать нагрузку один раз. Покупатели — через NPS после запуска |

## 3. Детальный анализ каждого стейкхолдера

### ❶ CPO (Chief Product Officer) — Александр Иванов

| Параметр | Описание |
|----------|----------|
| **Роль в проекте** | Заказчик. Выделяет бюджет, утверждает Scope, принимает результат |
| **Ключевой интерес** | Рост GMV (Gross Merchandise Volume) за счёт выхода в регионы. Снижение стоимости доставки на 25%. Повышение NPS покупателей |
| **Что для него успех** | Через 3 месяца после запуска: +50 городов доставки, средний чек в регионах не ниже, чем в столицах |
| **Что для него провал** | Запуск задерживается → конкуренты занимают регионы. Баги на проде → негативные отзывы в App Store |
| **Главная боль** | Бизнес теряет деньги на каждом часе задержки запуска |
| **Как с ним работать** | Короткие еженедельные демо (15 минут). Говорить на языке бизнеса: деньги, пользователи, конкуренты. Не грузить техническими деталями |
| **Что может заблокировать** | Может сменить приоритеты и перебросить бюджет на другой проект, если не видит прогресса |

---

### ❷ CTO (Chief Technology Officer) — Борис Петров

| Параметр | Описание |
|----------|----------|
| **Роль в проекте** | Технический спонсор. Выделяет команду разработки, утверждает архитектуру, отвечает за стабильность прода |
| **Ключевой интерес** | Надёжная асинхронная интеграция. Отсутствие техдолга. Минимальная связанность (coupling) с внешним сервисом |
| **Что для него успех** | Интеграция не роняет прод при пиковых нагрузках. Код покрыт тестами. Документация понятна дежурной смене |
| **Что для него провал** | Инцидент на проде из-за интеграции. Неконтролируемая нагрузка на БД. Вебхуки FastDelivery «вешают» API маркетплейса |
| **Главная боль** | Разработчики не читают ТЗ и делают «как проще», а не «как правильно» |
| **Как с ним работать** | Архитектурный комитет раз в 2 недели. Показывать диаграммы, а не текст. Обсуждать риски и fallback-стратегии |
| **Что может заблокировать** | Может отклонить архитектурное решение и отправить на переработку |

---

### ❸ Руководитель отдела логистики — Виктор Сидоров

| Параметр | Описание |
|----------|----------|
| **Роль в проекте** | Бизнес-пользователь. Его отдел будет работать с системой каждый день |
| **Ключевой интерес** | SLA доставки соблюдается. Скорость обработки заказов максимальная. Ручного труда — ноль |
| **Что для него успех** | Не нужно выгружать CSV. Трек-номера появляются в OMS мгновенно. Возвраты обрабатываются автоматически |
| **Что для него провал** | Интеграция есть, но при ошибках всё равно нужно писать в поддержку FastDelivery вручную |
| **Главная боль** | Сейчас тратит 3 часа в день на рутину (выгрузка CSV, внесение треков, ответы на вопросы поддержки) |
| **Как с ним работать** | Интервью в начале проекта: узнать реальные процессы AS-IS. Приглашать на UAT. Спрашивать про крайние случаи |
| **Что может заблокировать** | Может не принять систему на UAT, если интерфейс неудобен или не хватает статусов |

### ❹ Техлид FastDelivery — Глеб Смирнов

| Параметр | Описание |
|----------|----------|
| **Роль в проекте** | Внешний поставщик API. Его команда будет реализовывать свою сторону интеграции |
| **Ключевой интерес** | Чёткий API-контракт, который не будет меняться каждую неделю. Минимальные доработки существующего API |
| **Что для него успех** | Контракт согласован с первого раза. Нагрузка от MarketHub предсказуема. Нет срочных хотфиксов |
| **Что для него провал** | MarketHub меняет требования на ходу → постоянные переработки. Нагрузка в 10 раз выше ожидаемой → деградация API |
| **Главная боль** | Клиенты, которые не читают документацию и задают вопросы, на которые уже есть ответ |
| **Как с ним работать** | Еженедельные созвоны. Все изменения контракта — через Jira/Confluence, а не в чате. Предоставить оценку нагрузки до старта |
| **Что может заблокировать** | Может отказаться от нестандартных доработок. Может не успеть к сроку |

---

### ❺ DBA MarketHub — Дмитрий Кузнецов

| Параметр | Описание |
|----------|----------|
| **Роль в проекте** | Внутренний эксперт по базам данных. Отвечает за стабильность прода |
| **Ключевой интерес** | Отсутствие блокировок таблиц. Нагрузка в пределах нормы. Репликация не отстаёт |
| **Что для него успех** | Интеграция не создаёт дополнительной нагрузки > 5% к текущей |
| **Что для него провал** | Полная блокировка таблицы заказов из-за кривого запроса. Лаг репликации > 10 секунд |
| **Главная боль** | Разработчики не показывают планы запросов (EXPLAIN) до релиза |
| **Как с ним работать** | Показать все SQL-запросы до разработки. Согласовать регламент синхронизации. Объяснить, почему пишем именно так |
| **Что может заблокировать** | Может запретить прямой доступ к продовой БД. Может потребовать отдельную реплику |

### ❻ Главный бухгалтер — Елена Васильева

| Параметр | Описание |
|----------|----------|
| **Роль в проекте** | Пользователь отчётов. Будет использовать результаты автоматической сверки |
| **Ключевой интерес** | Суммы в актах совпадают с суммами в OMS. Расхождения выявляются автоматически. Формат актов соответствует 1С |
| **Что для неё успех** | Вместо 2 дней ручной сверки — 5 минут на проверку автоматического отчёта |
| **Что для неё провал** | Автоматическая сверка есть, но не совпадают суммы → всё равно ручная проверка |
| **Главная боль** | Каждый месяц вручную сопоставляет 15 000 строк из двух систем |
| **Как с ней работать** | Интервью в начале: какой формат нужен для 1С. Показать прототип отчёта. Согласовать маппинг полей |
| **Что может заблокировать** | Может не принять систему, если формат актов не совместим с бухгалтерским ПО |

## 5. Риски, связанные со стейкхолдерами

| Риск | Связанный стейкхолдер | Вероятность | Влияние | Mitigation |
|------|:---:|:---:|:---:|------|
| Смена приоритетов → потеря бюджета | CPO | Средняя | Критичное | Еженедельные демо прогресса, быстрые победы (quick wins) |
| Отклонение архитектурного решения | CTO | Низкая | Высокое | Раннее согласование архитектуры, до старта разработки |
| Непринятие системы на UAT | Руководитель логистики | Средняя | Высокое | Вовлекать с первого дня, показывать прототипы экранов |
| Невозможность реализовать требования к API | Техлид FastDelivery | Средняя | Высокое | Совместная проработка контракта, компромиссы по нестандартным методам |
| Блокировка прямого доступа к продовой БД | DBA | Низкая | Среднее | Согласовать регламент синхронизации заранее |
| Несовместимость формата актов с 1С | Главный бухгалтер | Средняя | Среднее | Интервью и согласование маппинга полей до разработки |
