# UC-02: Отслеживание статуса доставки

> **Проект:** Интеграция MarketHub ↔ FastDelivery
> **Приоритет:** Should Have (основной путь — вебхуки; поллинг — fallback)
> **Автор:** Системный аналитик
> **Дата:** Июнь 2026

---

## Primary Actor
**Покупатель MarketHub** — хочет знать, где его заказ.

## Stakeholders & Interests

| Стейкхолдер | Интерес |
|-------------|---------|
| **Покупатель** | Хочет в реальном времени видеть движение заказа, не обращаясь в поддержку |
| **Служба поддержки MarketHub** | Хочет снизить количество обращений «Где мой заказ?» |
| **Руководитель логистики** | Хочет видеть заказы, которые «зависли» в одном статусе дольше нормы |
| **CTO MarketHub** | Хочет, чтобы вебхуки FastDelivery не перегружали API маркетплейса |
| **FastDelivery** | Хочет, чтобы MarketHub корректно обрабатывал вебхуки и не создавал лишнюю нагрузку поллингом |

## Preconditions
1. Заказ успешно создан в FastDelivery (UC-01 выполнен)
2. В OMS сохранён `deliveryOrderId` и `trackingNumber`
3. Интеграционный сервис MarketHub подписан на вебхуки FastDelivery
4. Эндпоинт для приёма вебхуков развёрнут, доступен и защищён (mTLS)

## Trigger
**Основной:** FastDelivery отправляет вебхук `order.status.updated` при смене статуса заказа.

**Резервный:** Покупатель открывает страницу заказа в Личном кабинете → OMS проверяет актуальность статуса.

## Main Success Scenario (вебхук)

| Шаг | Система | Действие |
|:---:|---------|----------|
| 1 | FastDelivery | При смене статуса заказа отправляет вебхук `POST /webhooks/fastdelivery/status` |
| 2 | FastDelivery | В теле вебхука: `deliveryOrderId`, `trackingNumber`, `newStatus`, `timestamp`, `location` (опционально), `comment` (опционально) |
| 3 | Интеграционный сервис | Проверяет подпись вебхука (HMAC), валидирует `deliveryOrderId` (существует в OMS) |
| 4 | Интеграционный сервис | Обновляет статус заказа в OMS |
| 5 | OMS | Отправляет push-уведомление покупателю (если статус значимый: «В пути», «Доставлен») |
| 6 | FastDelivery | Получает `200 OK` от MarketHub. Если 200 не получен — повторяет отправку (at least once) |

## Маппинг статусов FastDelivery → OMS MarketHub

| Статус FastDelivery | Статус OMS | Видим покупателю | Push-уведомление |
|---------------------|------------|:---:|:---:|
| `PENDING` | «Ожидает курьера» | ✅ Да | Нет |
| `PICKUP` | «Курьер забрал заказ» | ✅ Да | Да: «Курьер забрал ваш заказ» |
| `IN_TRANSIT` | «В пути» | ✅ Да | Да: «Заказ в пути» |
| `OUT_FOR_DELIVERY` | «Передан курьеру для вручения» | ✅ Да | Да: «Курьер выехал к вам» |
| `DELIVERED` | «Доставлен» | ✅ Да | Да: «Заказ доставлен!» |
| `DELIVERY_FAILED` | «Не удалось доставить» | ✅ Да | Да: «Не удалось доставить заказ» |
| `CANCELLED` | «Отменён» | ✅ Да | Да: «Доставка отменена» |
| `RETURNING` | «Возвращается» | ✅ Да | Да: «Заказ возвращается продавцу» |

## Alternative Flows

### 1a. Вебхук не дошёл (сбой сети на стороне FastDelivery)
1. FastDelivery не получил `200 OK` в течение 5 секунд
2. FastDelivery выполняет ретрай с экспоненциальной задержкой: 1 мин → 5 мин → 15 мин → 30 мин
3. Если после 4 попыток вебхук не доставлен → заказ помечается в FastDelivery как «Проблема с интеграцией»
4. MarketHub обнаруживает пропущенный статус при следующем поллинге (см. Резервный сценарий)

### 2a. Некорректная подпись вебхука
1. Интеграционный сервис обнаруживает несовпадение HMAC-подписи
2. Возвращает `401 Unauthorized`
3. Логирует инцидент (возможная атака или сбой конфигурации)
4. Отправляет алерт дежурной смене MarketHub и техподдержке FastDelivery

### 3a. `deliveryOrderId` не найден в OMS
1. Вебхук содержит `deliveryOrderId`, которого нет в OMS
2. Интеграционный сервис возвращает `404 Not Found`
3. Логирует инцидент
4. Возможные причины: тестовый заказ из песочницы, ошибочный вебхук, рассинхрон данных
5. Дежурная смена разбирает вручную

### 4a. Дублирование вебхука (at least once)
1. FastDelivery отправляет вебхук повторно (предыдущий 200 OK потерялся в сети)
2. Интеграционный сервис проверяет текущий статус заказа в OMS
3. Если статус уже совпадает с тем, что в вебхуке → игнорирует, возвращает `200 OK`
4. Если статус из вебхука «новее» по бизнес-логике → обновляет

## Резервный сценарий: поллинг (Polling)

**Trigger:** Покупатель открывает страницу заказа в Личном кабинете. ИЛИ OMS по расписанию проверяет заказы, по которым не было вебхуков > 1 часа.

| Шаг | Система | Действие |
|:---:|---------|----------|
| 1 | OMS / Интеграционный сервис | Отправляет запрос `GET /v1/orders/{deliveryOrderId}/status` |
| 2 | FastDelivery | Возвращает текущий статус заказа |
| 3 | Интеграционный сервис | Сравнивает со статусом в OMS |
| 4 | Интеграционный сервис | Если статус изменился → обновляет OMS, отправляет push |
| 5 | OMS | Отображает актуальный статус покупателю |

### Ограничения поллинга
- **Частота поллинга по расписанию:** не чаще 1 раза в 15 минут на один заказ
- **Поллинг по запросу покупателя:** не чаще 1 раза в 30 секунд на одного покупателя (rate limiting)
- **Массовый поллинг:** запрещён. Не более 100 заказов в одном batch-запросе (если FastDelivery поддерживает batch)

## Postconditions (после успешного обновления статуса)
- Статус заказа в OMS актуален
- Покупатель видит движение заказа в Личном кабинете
- При значимых статусах — push-уведомление отправлено
